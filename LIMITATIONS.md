# Limitations

For an engineer deciding whether to run this in production. Each entry says
what does not work, why, what closing it takes, and whether it is a gap in
the design or just work not done. Everything here applies to every generated
app, because none of it lives in `apps/`.

Two things are **structural**: the audit guarantee ends at the Python process,
and the raw-SQL guard is a keyword filter. Neither can be fixed inside this
codebase; both need the database to enforce what Python currently promises.
Everything else is **unbuilt**: the seam exists, the code does not.

---

## Structural

### The audit trail stops at the process boundary

**What.** Any write that does not go through this Python process's SQLAlchemy
engine is invisible to the audit log: `sqlite3 app.db`, a second service on
the same file, a DBA, a cron job, a restore from backup. The `audit_log` table
itself is a plain table the same connection can `DELETE` from.

**Why.** Enforcement is `foundation/write_guard.py`: SQLAlchemy event hooks on
`before_flush`, `before_execute` and `before_cursor_execute` that raise unless
the write is inside `audit.write()`. Hooks live in the process. The database
does not know they exist.

**Closing it.** Move enforcement into the database: per-table triggers that
refuse `INSERT/UPDATE/DELETE` unless a session variable set by `audit.write()`
is present, an append-only `audit_log` (revoke `UPDATE/DELETE` from the
application role), and a separate migration role that is the only one allowed
to bypass. SQLite has triggers but no roles, so this means PostgreSQL. The
Python guard stays as the fast, readable failure; the trigger becomes the
guarantee. Roughly: one migration adding triggers per app table, generated by
the scaffold alongside the table; a role split in the deployment.

### Migrations opt out of the audit

**What.** `migrations/env.py` wraps every Alembic run in
`raw_writes_allowed()`. A migration can `UPDATE` or backfill any row with no
audit entry, and this is the documented way to make schema changes.

**Why.** Creating tables and altering columns cannot go through
`audit.write()`; the escape hatch is necessary, and once it is open for DDL
it is open for DML in the same run.

**Closing it.** Same fix as above: with database-level triggers, a migration
role can be granted DDL but not the bypass for DML on app tables, so a
backfill has to write audit rows explicitly (the scaffold's `migration.py.j2`
can emit a helper for that). Until then, review every migration for data
writes by hand.

### The raw-SQL guard is keyword matching, not parsing

**What.** For `session.execute(text(...))` and driver-level statements, the
guard strips `--` and `/* */` comments, splits on `;`, lowercases, and rejects
a statement whose first word is `insert/update/delete/replace/merge/...`, or a
`with` statement containing one. It has been hardened against the obvious
evasions (comments, CTEs, multi-statement strings) and there is a test for
each. It is still a regex over words, not a SQL parser. Dialect features it
does not model — `PRAGMA writable_schema`, `ATTACH DATABASE`, `VACUUM INTO`,
string literals that happen to contain `;` — are either allowed or produce
false positives.

**Why.** ORM and Core writes are intercepted structurally and cannot slip
past. Raw text has no structure to intercept; a correct decision needs a
dialect-aware parser, and none is a dependency here.

**Closing it.** Either forbid `text()` writes outright (reject any `text()`
statement outside `raw_writes_allowed()`, which is a two-line change and what
a strict deployment should do), or accept that the guard is defence in depth
and put the real guarantee in database triggers as above. Adding a real SQL
parser (`sqlglot`) would make the filter better but still not a guarantee.

## Unbuilt

### Authentication is mocked; the actor is whoever the client says

**What.** The current user is the integer in the unsigned `current_user_id`
cookie. Anyone who can reach the app can set it to the admin's id. Every
role check, every sensitive-field filter, every audit `actor_id` trusts that
number. The "Acting as" dropdown in the header is a UI for doing exactly this.

**Why.** Deliberate for the demo: switching roles is how you see the
foundation work, and the project brief asked for it.

**Closing it.** Replace `foundation/auth.py::current_user` with a real
session: OIDC/SAML against the company IdP, a signed (`itsdangerous`) or
server-side session cookie, and a `users` table populated from the IdP
instead of the seed. Remove `/switch-user` and the partial. Nothing else in
the codebase depends on how the current user is established; the change is
contained to that module and the layout. Until it is done, do not put this
on a network anyone untrusted can reach.

### SQLite, and no deployment story

**What.** The database is `./app.db`. There is no Dockerfile, no process
manager config, no production settings module, no backup, no secrets
handling, no health check beyond `GET /health`, no logging configuration, no
metrics, no TLS termination. `uvicorn foundation.app:app` on a laptop is the
only way it has ever run.

**Why.** Scope. The repo was built to answer "can we own the platform layer",
not to ship one.

**Closing it.** PostgreSQL (needed anyway for the audit triggers; the code
uses standard SQLAlchemy and Alembic, and `DATABASE_URL` in
`foundation/config.py` is the only SQLite-specific thing), a container image,
one migrations job that runs `alembic upgrade head` before the app starts,
structured logging, and whatever the company already uses for secrets,
backups and observability. One to two days for someone who has done it
before; none of it touches `apps/`.

### Two reviewers can both approve the same case, if they do it at the same instant

**What.** Two reviewers open the same pending case and both click Approve.
Normally the first wins and the second gets a 409 ("already moved by someone
else") and is sent back to the queue: the decision form posts the state it
was rendered with (`expected=pending`) and `decide_row` compares it to the
row before writing. That closes the realistic case, a page left open for
minutes while a colleague decides.

It does **not** close the race. If both POSTs arrive within the same few
milliseconds, both handlers read `pending` before either writes, both
comparisons pass, both writes succeed, and the audit log shows two
`pending → approved` entries by two actors — the second recording a `before`
that was already stale. No error is raised anywhere. The generic **edit form**
has no guard at all: two people saving the same record means the second save
wins field by field.

**Why.** The check is read-then-compare in Python, not a conditional write.
Nothing tells the database "only if still pending". SQLite serialises
writers so the window is a few milliseconds, but it exists, and on
PostgreSQL with real concurrency it widens.

**Closing it.** A `version` column on every generated model, incremented by
`audit.update`, and `UPDATE ... WHERE id = :id AND version = :seen` with a
rowcount check inside `audit.write()`. One change in `foundation/audit.py`,
one in `scaffold/templates/model.py.j2`, one migration per existing app. Do it
when moving to PostgreSQL, where concurrent writers are real.

### Search and sort are what the SQL `LIKE` gives you

**What.** Search is case-insensitive substring over the app's text columns
(`%`, `_` and `\` are escaped). It does not search foreign-key labels (a
reviewer's name), numbers, dates or enum labels, and there is no full-text,
no saved filters, no multi-column sort. Sort is one column at a time by
clicking a header.

**Why.** It was the cheap, load-bearing version. Anything more needs the
spec to say which columns matter or the database to index them.

**Closing it.** `searchable: true` / `sortable: true` per field in the spec,
generated joins for fk labels, indexes in the generated migration, and
PostgreSQL full-text or an external index if a table grows past tens of
thousands of rows.

### No pagination

**What.** Every list view loads every matching row. The default "Needs
decision" tab is bounded by how many cases are open; "All" is not.

**Why.** Small data was the stated scope.

**Closing it.** `limit/offset` (or keyset on `id`) in the generated list
route plus a pager in `partials/table.html`. Foundation and generator change,
no spec change; every app inherits it on regeneration.

### Wide tables scroll sideways

**What.** Tables overflow horizontally inside their card. The five current
apps fit at 1366px; an app with fifteen fields will scroll.

**Why.** Nothing in the spec says which columns matter in the list.

**Closing it.** A `list: false` flag per field (hide from the list, keep on
detail), or a responsive card layout below a breakpoint. Spec + generator
change.

### The activity feed does N+1 lookups

**What.** The home page's audit feed resolves foreign-key values to labels
one query per changed fk per entry. It shows the latest 25 entries, so this
is bounded, but each home page load is dozens of queries.

**Closing it.** Batch the lookups per table before rendering
(`foundation/audit_view.py`), or denormalise the label into the audit `after`
payload at write time. Half a day.

### Unexpected errors are FastAPI's default 500

**What.** 404, 403, 400, 409 and validation errors render a friendly page
(HTML clients) or JSON (API clients). An unhandled exception — a bug, a
database outage — returns Starlette's plain-text `Internal Server Error`
with a traceback in the server log only.

**Closing it.** One `@app.exception_handler(Exception)` rendering
`error.html` and reporting to whatever error tracker the deployment uses.

### "Decided today" is team-wide, in UTC

**What.** The count on a queue's stats strip is every transition into a
closed state, by anyone, since 00:00 UTC. It is not "what I decided" and it
resets at a time that is not midnight for most of the team.

**Closing it.** Filter `AuditLog.actor_id` by the current user and take the
day boundary from a configured timezone. Generator change only.

### Discovery metadata is a naming convention

**What.** `foundation/discovery.py` reads `TITLE`, `DESCRIPTION`, `SINGULAR`,
`MODEL`, `WORKFLOW_FIELD` and `OPEN_STATES` from each `routes.py` with
`getattr(..., default)`. Rename or delete one while hand-editing and nothing
errors; the home page shows the wrong title, a zero count, or no queue badge.
The README documents each name; nothing enforces them.

**Closing it.** Make discovery fail loudly: require an explicit `APP =
AppMeta(...)` dataclass in `routes.py`, or have a test iterate `apps/` and
assert each name is present. A morning's work; the second option needs no
change to generated code.

### Regeneration cannot merge

**What.** After you hand-edit a generated file, the generator leaves it alone
forever (`kept`). A later spec change — a new field — reaches the untouched
files and stops at the edited one, so a hand-edited `routes.py` will not know
about the new column until you add it yourself.

**Why.** Hash-based protection is what guarantees hand edits are never
destroyed; a three-way merge was not worth the risk to that guarantee.

**Closing it.** Keep the previous generated output alongside the manifest
and offer a three-way merge (`git merge-file`) on regeneration, leaving
conflict markers instead of refusing. Scaffold-only change.
